# ADR 0001：建立社区开发文档与贡献治理入口

- 状态：accepted
- 日期：2026-09-23
- 参与讨论：rockythink
- 取代：无
- 被取代：无

## 背景

RelyLess 已从个人维护项目转为面向 GitHub 社区协作的项目。README 能说明产品和安装，但无法稳定承载产品边界、工程原则、架构决策、开发记录和 PR 审查要求。不同开发者或 AI 工具若只从局部代码推断规则，容易产生第二套交互、扩大数据范围或遗漏浏览器验证。

## 决策驱动因素

- 社区贡献者需要一个明确且可逐步阅读的入口；
- 产品方向、当前行为和历史原因需要分开记录；
- GitHub 原生文件应直接引导 Issue 与 PR；
- 人类开发者和 AI 编程工具应引用同一组事实来源；
- 文档维护成本必须低于它避免的重复讨论和回归成本。

## 备选方案

### 只扩充 README

入口简单，但 README 会持续膨胀，产品使用说明与开发治理难以独立演进。

### 使用外部 Wiki

适合大量教程，但文档不能与代码在同一 PR 原子更新，也不利于离线审查和版本对应。

### 仓库内开发文档中心

以 `docs/development/` 为索引和规范中心，保留 GitHub 识别的根目录贡献文件，并让 Agent 指令只引用规范、不复制规范。

## 决策

采用仓库内开发文档中心：

- `docs/development/` 保存产品方向、开发原则、架构、PR 规则、开发记录和 ADR；
- `CONTRIBUTING.md`、`.github/` 模板提供 GitHub 社区入口；
- `AGENTS.md` 与 `.agents/skills/` 为 AI 工具提供最短执行路径，并链接同一规范；
- README 只保留开发入口和常用命令，不复制全部规则。

## 结果

### 正面影响

- 产品、工程和审查边界可以独立更新并随代码评审；
- 重要决定和实现证据有固定位置；
- 人类与 AI 贡献者使用同一套约束；
- PR 可以明确检查文档、隐私、UI 和验证影响。

### 代价与风险

- 维护者必须在行为改变时同步文档；
- 文档可能过期，需要 PR 模板和审查规则持续提醒；
- 小改动若被要求写过多记录会阻碍贡献，因此开发记录和 ADR 都只针对高影响改动。

## 实施与验证

本决策由建立开发文档中心、贡献指南、PR/Issue 模板、Agent 指令和链接检查的同一批改动执行。验证要求是仓库内链接可解析、`npm run check` 通过、模板没有与现有脚本或产品行为冲突。
